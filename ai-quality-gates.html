Adding AI review to CI/CD without trusting it blindly

A design proposal, written as an architecture decision record, for layering AI-assisted review on top of deterministic quality and security gates.

Status
Proposed
Date
September 2026
Author
Islem Haddad

I build Jenkins pipelines and run Argo CD in production. Teams now write more code with AI agents than people can carefully review, so the pipeline has to carry more of the judgment. I have already worked this way on a smaller scale: I built Davy Jones with AI pairing, behind a written plan and a compile and typecheck gate after every phase. This is how I would design the same idea for a team's pipeline, in the format I would use to propose it.

Context

Picture a small senior team where humans and AI agents both write code. Writing is no longer the slow part. Review is.

Most quality gates today are deterministic. They answer questions like "is it formatted", "do the tests pass" and "does it pull in a known vulnerability" very well. They cannot answer "is this change risky", "is the rollback path clear" or "does the runbook still match what the code does". Those questions land on human reviewers, who are the scarcest resource on the team.

The example stack for this proposal is Rust services and a React frontend on managed Kubernetes in Google Cloud, with Terraform for infrastructure and Argo CD for delivery. The ideas carry over to any CI system: GitHub Actions, GitLab CI or Jenkins.

Decision drivers

  • Nothing reaches production on an AI's word alone.
  • Every gate is code: versioned, reviewed, and runnable on a laptop with the same result as in CI.
  • Policy is enforced twice, in the pipeline and at the cluster. Under GitOps the cluster is the last gate, so it has to hold on its own.
  • A gate earns trust with measured results, not with assumptions.
  • When a gate fails, it says how to fix the problem.

Options considered

Deterministic gates only

Predictable, cheap and well understood. But every judgment call still falls on people, and that stops scaling once AI agents multiply the number of changes.

An AI reviewer that blocks from day one

It would catch more, but model output is not deterministic, it can be confidently wrong, and it can be steered by text hidden in the pull request itself (prompt injection). A noisy gate that blocks merges teaches people to ignore it or work around it, which is worse than having no gate.

Layered gates (chosen)

Deterministic checks block. AI checks advise. An AI check is promoted to blocking only after it has proven precise on real pull requests, and it is demoted again if its precision drops.

Decision

Adopt the layered model across four passage points. Every change moves through them in order.

What the AI reviewer does

It reads the diff, the pull request description and the repository's written rules: the contributing guide, the ADR index and any runbook the change touches. It returns JSON that is validated against a schema and posted as a single comment with four parts:

  • Risk level (low, medium or high) with one sentence explaining why.
  • Findings tied to a file and line, each one a question a senior reviewer would ask.
  • Missing writing: behavior changed, but no ADR, runbook or doc changed with it. If it is not written down, it does not exist.
  • Rollback: for migrations and infrastructure changes, whether the way back is stated.

It never approves. Approval stays with a person.

A second, lower-risk use is the failure explainer. When a blocking gate fails, the model reads the job log and posts the likely cause and fix. It saves time on every red build and cannot let anything bad through.

Guardrails

  • Model output is untrusted input. The AI job runs in an isolated runner with a read-only token and no secrets, and it cannot approve or merge. The prompt tells the model that pull request content is data, not instructions, but the permissions are what actually enforce it.
  • Everything is auditable. Pin the model version and log each prompt and response, so any finding can be traced and a change in behavior can be tied to a model update.
  • Cost and latency stay bounded. Run on pull requests only, skip documentation-only changes, cap the diff size, and run in parallel with the other checks so it is never on the critical path.
  • Know where the code goes. Confirm the provider's data retention terms before sending source code, or use a self-hosted model for sensitive repositories.

How an AI check earns the right to block

Every AI finding is resolved as either fixed or dismissed, which gives a precision score for each type of check. A check is promoted to blocking only when it stays above about 90% precision for at least four weeks, over enough findings to mean something. It is demoted if it drops below that. Even a blocking AI check can be overridden by a person, with the reason recorded. The 90% figure is a starting point for the team to tune, not a rule.

Consequences

Positive

  • Reviewers spend their time on design and risk instead of things a machine can find.
  • Documentation stays current, because drift is flagged on every pull request.
  • Security policy holds even if one layer is bypassed, because it is enforced in both the pipeline and the cluster.
  • Decisions about which gates to keep are backed by data.

Negative

  • The gates themselves become a product that needs an owner and maintenance.
  • Model usage costs money and adds a dependency on a provider.
  • Advisory checks will be noisy at first, until prompts and thresholds are tuned.

Rollout

  1. Weeks 1 and 2: deterministic pull request and build gates. Kyverno policies in audit mode, to see what would break before anything is blocked.
  2. Weeks 3 and 4: Kyverno moves to enforce. The AI reviewer and failure explainer go live, advisory only, on one repository.
  3. Weeks 5 to 10: measure precision, tune prompts, extend to the other repositories.
  4. After that: promote the checks that earned it, and revisit this ADR with the numbers.

How we will know it works

Track the DORA metrics that matter here, change failure rate and lead time for changes, alongside three pipeline-specific ones: time from a red build to a fix, the share of AI findings that get fixed rather than dismissed, and the number of incidents where the runbook was missing or wrong.

If the change failure rate does not fall, or lead time goes up, the design is wrong and this record gets revised. That is the point of writing it down.
